# QR-03: Release A Runtime And Keep No Learner Code

A debug session that ends mid-run releases its runtime within one minute and keeps no learner code on the server.

- **Status:** Active
- **Characteristic:** Security
- **Sub-characteristic:** Resistance
- **Business importance:** High
- **Technical risk:** High

## Scenario

### Source

A testing session ends mid-run, whether the learner's code raised an exception (non-dangerous), consumed all of the runtime's resources (dangerous), or the learner disconnected before the runtime was torn down.

### Stimulus

The learner's VS Code disconnects, the session times out, or the learner's code behaves unexpectedly (an exception or resource exhaustion) while a `debug-runtime` container is running the learner's edited source.

### Environment

The product runs on the single VM of [`CON-01`](../../product-vision.md#con-01) under the API-key budget of [`CON-02`](../../product-vision.md#con-02), and a learner may have several runtimes over a day.

### Artifact

The `debug-runtime` container, the sandbox that caps its resources ([`DEC-016`](../../decisions.md#dec-016)), and the `webapp`'s session management that owns the runtime's lifecycle.

### Response

The product shall reclaim the runtime and delete the learner's uploaded source, so a later learner cannot read or run a previous learner's code, and an unexpected program shall not crash the server.

### Response Measure

Within one minute of a session ending — whether by an exception, resource exhaustion, or disconnect — the runtime is stopped and its filesystem is removed, and no learner source remains on the server; a fresh session starts from a clean runtime.
The reclaimed resource count matches the sessions that ended, and a run that exhausts resources is contained rather than taking down the product.

## Critical Modules

The session lifecycle and the source upload live in [`app/main.py`](../../../app/main.py) (the exercise and verify endpoints).
The acceptance of this requirement is a candidate for `QR-02`'s testability story.

## QRT-03

The local verification runner removes its temporary workspace after both normal completion and a timed-out execution.

- **Status:** Active
- **Level:** scripted
- **Runs at:** A developer machine with the Python development dependencies installed.
- **Command:** `python -m pytest tests/test_runtime_cleanup.py -q`

### Procedure

1. Run the dedicated runtime-cleanup tests from the repository root.
2. Confirm that a normally completed verification leaves no temporary workspace behind.
3. Confirm that a deliberately non-terminating learner program times out and its temporary workspace is removed.

**Pass when:** Both cleanup tests pass, the temporary verification directory no longer exists after completion or timeout, and a timed-out verification does not run beyond the configured timeout.

## QRT-04

The deployed debug session releases its runtime and removes the corresponding learner source after an exception, resource exhaustion, or learner disconnect.

- **Status:** Active
- **Level:** manual
- **Runs at:** The staging deployment, from a campus-connected machine with authorized access to inspect the staging VM's runtime containers and session storage.

### Procedure

1. Record the deployed staging commit and a baseline list of runtime containers and session-storage entries.
2. Start an exercise and record the runtime/container and session-storage entry created for that run, if the implementation exposes them.
3. Repeat the scenario with a program exception, controlled resource exhaustion, and learner disconnect. Do not run destructive resource-exhaustion code against production.
4. Within 60 seconds of each session ending, check that its runtime has stopped and its session filesystem/source has been removed.
5. Start a new session and verify that it cannot access source from a previous session.
6. Record the outcome for every termination case, including cases that cannot be executed because the current deployment has no corresponding runtime/session lifecycle mechanism.

**Why Manual:** The current public product API does not expose a session/runtime identifier or a machine-readable cleanup event. This check requires coordinating real VS Code disconnect/termination scenarios with inspection of the deployed host's container and session-storage state. The scripted QRT-03 only covers the local verification subprocess and temporary directory, not remote runtime lifecycle cleanup.

**Pass when:** For all three termination scenarios, the associated staging runtime stops and its filesystem/source is removed within 60 seconds, and a new session cannot access any source from the ended session.
