# QR-02: Testable Generator And Harness From A Clean Checkout

A developer can run the checks that cover the generator and the harness from a clean checkout, and a broken change fails them.

- **Status:** Active
- **Characteristic:** Maintainability
- **Sub-characteristic:** Testability
- **Business importance:** High
- **Technical risk:** Medium

## Scenario

### Source

A developer on the Debugging Gym team, after the course, who has cloned the repository on a fresh machine.

### Stimulus

The developer runs the repository's check command for the product code with no prior environment, following the setup page.

### Environment

A clean checkout on the developer's machine with the Python toolchain from [`docs/setup.md`](../../setup.md) installed, and no cached build artifacts.

### Artifact

The `webapp`'s generator module [`app/generator.py`](../../../app/generator.py) and the harness runner [`app/harness_runner.py`](../../../app/harness_runner.py).

### Response

The check command shall run the full product test suite and report which generator or harness behavior changed, without the developer opening any story or requirement.

### Response Measure

From a clean checkout, `python -m pytest tests/ -q` completes in under a minute and passes; a change that breaks the generator or harness fails at least one test.
The `Maintainability` / `Testability` pair is `High` business importance because the instructors are stakeholders and the course is part of the business, so the product's checks must survive the term.

## Critical Modules

The critical modules this requirement names are the frontend entry point [`app/static/app.js`](../../../app/static/app.js) (which drives the connect-and-verify flow in the browser) and the generator module [`app/generator.py`](../../../app/generator.py) (which produces every exercise).
Both must be covered by the clean-checkout test suite above.
