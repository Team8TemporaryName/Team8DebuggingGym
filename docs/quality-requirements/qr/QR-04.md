# QR-04: Stay Available 99.9% Once Deployed

The product stays available for 99.9% of a week once deployed to the production host.

- **Status:** Active
- **Characteristic:** Reliability
- **Sub-characteristic:** Availability
- **Business importance:** Medium
- **Technical risk:** High

## Scenario

### Source

A learner or instructor attempts to open the Debugging Gym in a browser during the week.

### Stimulus

The product is deployed on the production host and the learner requests the web app or a debug session.

### Environment

The product runs on the single VM of [`CON-01`](../../product-vision.md#con-01) alongside the `debug-runtime` containers, under the API-key budget of [`CON-02`](../../product-vision.md#con-02).

### Artifact

The `webapp` container serving the catalogue, generation, and verification, and the host that runs the `debug-runtime` containers.

### Response

The product shall serve the request and report the failure rather than hang when a runtime or the LLM provider is unavailable.

### Response Measure

The web app is reachable and serves a response in at least 99.9% of the minute-level checks in a week, measured from outside the host; a failure of a single `debug-runtime` does not take the whole product down.
The `Performance Efficiency` / `Time Behaviour` cost of a busy host stays below the response budget of [`QR-01`](QR-01.md) attach flow.

## QRT-05

The staging web application and problem-kind catalogue respond successfully during minute-level availability checks over a full seven-day observation window.

- **Status:** Active
- **Level:** deployed
- **Runs at:** The staging deployment, from a machine connected to the university network.
- **Command:** Set `STAGING_BASE_URL` to the private staging base URL, then run `python scripts/qrt_staging_availability.py --duration-seconds 604800 --interval-seconds 60 --evidence reports/week-05/evidence/qr-05-staging-availability.jsonl`.

### Procedure

1. Confirm staging is deployed and the checking machine is connected to the university network.
2. Set `STAGING_BASE_URL` in the local environment to the staging URL. Do not put the actual address in the command, QRT file, evidence JSONL, or other tracked repository file.
3. Run the command for the complete 604800-second observation window with one sample every 60 seconds.
4. During an approved staging-only fault-injection window, terminate one disposable debug runtime while the monitor is running. Record the fault-injection time separately; never perform this action against production.
5. Keep the emitted sanitized JSONL evidence file. It records timestamps, endpoint paths, response status, elapsed time, and failures, but not the private staging address. Inspect the samples around the fault-injection time.
6. Verify the final availability percentage printed by the monitor and include the evidence link in the quality requirement testing plan.

**Pass when:** At least 99.9% of the minute-level samples over the full seven-day window receive acceptable responses from both `/` and `/api/kinds`, and a single staging debug-runtime failure does not make either application endpoint unavailable.
