# QR-05: Diagnose A Failed Request From The Operating Signals

A failed request in the core task is diagnosable from the operating signals the product emits, so an operator can find why it failed.

- **Status:** Active
- **Characteristic:** Maintainability
- **Sub-characteristic:** Analysability
- **Business importance:** High
- **Technical risk:** Medium

## Scenario

### Source

A system operator, reacting to a failed request in the core task (choose, generate, solve, or verify) on the staging deployment.

### Stimulus

A request in the core task fails, and the operator wants to find the request's log point and its quality signal to diagnose the failure.

### Environment

The product runs on the staging deployment on the university VM, with the observability backend (OpenObserve) in the organization configured for staging, reachable by the operator from the university network.

### Artifact

The `webapp` container's per-request structured log line and the observability backend's staging organization that stores it and serves the `SLI` dashboard.

### Response

The product shall expose a per-request log point and a quality signal that the operator can query in the staging organization, so the failed request is traceable from its identifier to its route and failure label.

### Response Measure

Within five seconds of the failed request's response, a query of the staging organization returns one log point for it, carrying its `request_id`, `route`, and failure label; within one minute, the `SLI`'s query returns the failure series with a P95 value.

## Critical Modules

The per-request log line and the `SLI` live in [`docs/observability.md`](../../observability.md#sli-01), and the signal is emitted by the `webapp` container in [`app/main.py`](../../../app/main.py) and [`app/telemetry.py`](../../../app/telemetry.py).

## QRT-01

A failed request in the core task on the staging deployment is diagnosable: within five seconds a query of the staging organization returns its log point with `request_id`, `route`, and failure labels, and within one minute the `SLI`'s query returns the failure series with a P95 value.

- **Status:** Active
- **Level:** deployed
- **Runs at:** The staging deployment, from a machine on the university network, using `python scripts/check_sli.py` and reading the `SLI-01` signal ([`docs/observability.md#sli-01`](../../observability.md#sli-01)).

### Procedure

1. Confirm that the staging application's deployed `.env` has `OBSERVABILITY_ENABLED=true`, the OpenObserve organization identifier, the OpenObserve server base URL, and a valid ingestion credential. The local QRT also needs an OpenObserve API credential with read/query permissions; ingestion tokens cannot be used on stream-schema and search API endpoints. Use the Root account's Basic credential for this operator-run check when RBAC is not configured. A service account is an alternative only when it has been granted the required read/query permissions. Set `OBSERVABILITY_ORGANIZATION` to that same identifier in the local environment. Use the unique identifier shown for the staging organization in OpenObserve (IAM > Organizations), not its display name; the identifier is used in API paths. Also set `STAGING_BASE_URL`, `OPENOBSERVE_URL`, and `OPENOBSERVE_QUERY_TOKEN` locally. Set the latter to the Base64-encoded `username:password` for the Root account (or an authorized service account), or the complete `Basic ...` header. Do not use the app's ingestion token for these read queries. The current application does not set an OTLP `stream-name` header, so OpenObserve should store its logs in the `default` stream. Do not store private values in tracked files.
2. Ensure staging already contains at least one exercise, then run `python scripts/check_sli.py` from a machine connected to the university network. The script retrieves the existing exercise list and reuses one exercise; it does not authenticate as a teacher, create an exercise, or call the LLM provider.
3. Confirm that the script reports the expected HTTP 400 response and captures its `x-request-id`.
4. The script queries the staging OpenObserve log stream by that request ID and checks that exactly one point has the matching request ID, the verification route, and the `client_error` outcome within five seconds.
5. The script runs the existing SLI-01 five-minute P95 PromQL query against the staging organization's Prometheus-compatible API and checks that a numeric `client_error` verification series is returned within one minute.
6. Obtain the deployed staging commit separately over the authorized VM connection using `git -C ~/staging_app rev-parse HEAD`, and record it alongside the sanitized command output, measured values, and a staging dashboard screenshot. The commit SHA is evidence metadata, not a script input. Do not include private URLs, credentials, tokens, or other private configuration values.

**Pass when:** the staging organization's log query returns the failed request's log point (with its `request_id`, `route`, and failure label) within five seconds, and the `SLI`'s five-minute P95 query returns the failure series with a numeric value within one minute.
