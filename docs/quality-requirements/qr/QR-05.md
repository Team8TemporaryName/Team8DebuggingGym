# QR-05: Diagnose A Failed Request From The Operating Signals

A failed request in the core task is diagnosable from the operating signals the product emits, so an operator can find why it failed.

- **Status:** Active
- **Characteristic:** Maintainability
- **Sub-characteristic:** Analysability
- **Business importance:** High
- **Technical risk:** Medium

## Scenario

### Source

A system operator, reacting to a failed request in the core task (choose, generate, solve, or verify) on the staging deployment.

### Stimulus

A request in the core task fails, and the operator wants to find the request's log point and its quality signal to diagnose the failure.

### Environment

The product runs on the staging deployment on the university VM, with the observability backend (OpenObserve) in its `staging` organization, reachable by the operator from the university network.

### Artifact

The `webapp` container's per-request structured log line and the observability backend's staging organization that stores it and serves the `SLI` dashboard.

### Response

The product shall expose a per-request log point and a quality signal that the operator can query in the staging organization, so the failed request is traceable from its identifier to its route and failure label.

### Response Measure

Within five seconds of the failed request's response, a query of the staging organization returns one log point for it, carrying its `request_id`, `route`, and failure label; within one minute, the `SLI`'s query returns the failure series with a P95 value.

## Critical Modules

The per-request log line and the `SLI` live in [`docs/observability.md`](../../observability.md#sli-01), and the signal is emitted by the `webapp` container in [`app/main.py`](../../../app/main.py) and [`app/telemetry.py`](../../../app/telemetry.py).

## QRT-01

A failed request in the core task on the staging deployment is diagnosable: within five seconds a query of the staging organization returns its log point with `request_id`, `route`, and failure labels, and within one minute the `SLI`'s query returns the failure series with a P95 value.

- **Status:** Active
- **Level:** deployed
- **Runs at:** The staging deployment, from a machine on the university network, reading the `SLI-01` signal ([`docs/observability.md#sli-01`](../../observability.md#sli-01)).

### Procedure

1. Run the traffic-generation script `scripts/check-sli.ts`, which exercises the core task against the staging deployment, deliberately fails one request, and records its `request_id`, `route`, and failure label.
2. Within five seconds of the failed request's response, query the staging organization for the log point carrying that `request_id`; confirm it returns exactly one log line with the `route` and `outcome` labels.
3. Within one minute, run the `SLI-01` query `histogram_quantile(0.95, sum by (le, route, outcome) (rate(request_duration_ms_bucket[5m])))` against the staging organization and confirm it returns a numeric P95 for the failure series.
4. Capture the log-query output, the `SLI` query result, and the dashboard screenshot as evidence.

**Pass when:** the staging organization's log query returns the failed request's log point (with its `request_id`, `route`, and failure label) within five seconds, and the `SLI`'s five-minute P95 query returns the failure series with a numeric value within one minute.
