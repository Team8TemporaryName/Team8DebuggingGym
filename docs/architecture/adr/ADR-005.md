# ADR-005: Collect Analytics Events In The Web App Container

- **Status:** Accepted
- **Created:** 2026-11-07
- **Updated:** 2026-11-07
- **Containers:** `webapp`
- **Addresses:** [`FR-016`](../../functional-requirements/fr/FR-016.md)
- **Decision:** [`DEC-023`](../../decisions.md#dec-023)

## Context

The product needs to read its value from usage: how learners progress through the core task. The product must record an event for each step of the core task and send it to a self-hosted analytics backend, without collecting personal data and without breaking the product when telemetry is unavailable.

The events a learner generates on the `webapp` container are the closest observable to the skill-training action the product exists to produce.

## Considered Options

- **Instrument the `webapp` container with an HTTP POST per event.** The container is where the core-task actions happen, so it can record the events with the fields the plan defines, with collection disabled by default so telemetry can never break the product.
- **Instrument each container separately.** This would spread the events across containers and complicate the schema and the pipeline, without adding value.

## Decision Outcome

Chosen option: instrument the `webapp` container with an event-sending helper (`app/telemetry.py`) that posts each event to the analytics backend, off by default via `ANALYTICS_ENABLED`, and carries an opaque `learner_id` and a `source` field (`web`, `usability-test`, or `smoke`).

## Consequences

- **Where the data comes from:** the `webapp` emits the analytics events, matching the event table's `Collected at`.
- **Safety:** collection is disabled by default and telemetry failures are swallowed, so telemetry never breaks the product.
- **Privacy:** events carry only an opaque `learner_id`, never personal data.
- **One source of truth:** the event table in `docs/analytics.md` is the schema the instrumentation sends, so the table and the code must not disagree.
