
# ADR-005: Use OpenPanel for Privacy-Conscious Product Analytics

- **Status:** Accepted
- **Created:** 2026-11-12
- **Updated:** 2026-11-12
- **Containers:** `webapp`, `analytics`
- **Addresses:** [`FR-016`](../../functional-requirements/fr/FR-016.md)
- **Decision:** [`DEC-026`](../../decisions.md#dec-026)

## Context

Debugging Gym needs product analytics to understand learner engagement, exercise generation, and successful verification. Analytics must not interrupt core application behavior or collect sensitive learner data.

The product must record events for the steps of the core learner task and send them to an analytics provider without collecting personal information.

The project also needs separate staging and production analytics scopes so test traffic does not contaminate production metrics.

## Considered Options

- **Do not collect product analytics.** This avoids analytics infrastructure but provides no evidence about learner engagement or task completion.
- **Use OpenPanel.** This provides event collection and dashboards while allowing the application to send events through a documented tracking interface.
- **Build a custom analytics service.** This provides control but adds implementation and maintenance work beyond the project's current needs.
- **Instrument each container separately.** This would spread events across containers and complicate the schema and pipeline without adding value.

## Decision Outcome

Chosen option: use OpenPanel for event collection and dashboards, with event instrumentation in the `webapp` container.

The application uses an event-sending helper in `app/telemetry.py`. It validates event names, required properties, and event sources before delivery. Events carry a random opaque learner identifier and a source field (`web`, `usability-test`, or `smoke`).

Analytics delivery is best-effort. Missing credentials or delivery failures must not interrupt core application behavior. Collection must not send source code, exercise solutions, credentials, names, email addresses, or other directly identifying personal information.

Staging and production shall use separate OpenPanel projects or scopes with distinct credentials. Smoke events shall be sent only to staging and excluded from all product metric queries.

Deployment of the analytics platform, environment configuration, smoke-event verification, dashboard creation, and sanitized dashboard evidence are deferred to Sprint 7 because university VM access is currently unavailable. This is an infrastructure blocker, not a claim that deployment or dashboards have been completed.

## Consequences

- **Measurement:** the team can evaluate learner engagement and successful exercise completion.
- **Privacy:** analytics identifiers are opaque, and sensitive learner content is excluded.
- **Reliability:** analytics delivery failures do not block application workflows.
- **Environment isolation:** staging and production data remain separate.
- **Consistency:** the event schema in `docs/analytics.md` must agree with the instrumentation.
- **Deployment:** deployment, smoke-event verification, dashboards, and sanitized dashboard evidence remain Sprint 7 tasks.
