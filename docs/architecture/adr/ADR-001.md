# ADR-001: One Webapp, A Debug Runtime, A Managed Database, And A VS Code Extension

- **Status:** Accepted
- **Created:** 2026-10-24
- **Updated:** 2026-10-24
- **Containers:** `webapp`, `debug-runtime`, `database`, `vscode-extension`
- **Addresses:** [`FR-001`](../../functional-requirements/fr/FR-001.md), [`FR-002`](../../functional-requirements/fr/FR-002.md), [`FR-003`](../../functional-requirements/fr/FR-003.md), [`FR-004`](../../functional-requirements/fr/FR-004.md), [`FR-005`](../../functional-requirements/fr/FR-005.md), [`FR-006`](../../functional-requirements/fr/FR-006.md), [`FR-007`](../../functional-requirements/fr/FR-007.md), [`FR-008`](../../functional-requirements/fr/FR-008.md), [`FR-010`](../../functional-requirements/fr/FR-010.md), [`QR-02`](../../quality-requirements/qr/QR-02.md), [`QR-03`](../../quality-requirements/qr/QR-03.md)
- **Decision:** [`DEC-009`](../../decisions.md#dec-009), [`DEC-012`](../../decisions.md#dec-012)

## Context

The Debugging Gym lets a learner choose a problem kind, get an exercise, attach their own VS Code, and verify the fix against a harness. The Week 3 slice proved the riskiest part — attaching a learner's VS Code to a hosted runtime over the Debug Adapter Protocol — in Python with `debugpy`. 
The product must keep learner-submitted code isolated ([`DEC-016`](../../decisions.md#dec-016)) and ensure that official verification uses server-controlled tests independently of the learner-editable local harness ([`DEC-017`](../../decisions.md#dec-017)).
The product runs on the single VM of [`CON-01`](../../product-vision.md#con-01) under a small API-key budget.

## Considered Options

- **One monolithic webapp that also runs learner code.**
  Simple to run, but a learner's code would share a process with the product, breaking isolation and the release of [`QR-03`](../../quality-requirements/qr/QR-03.md).
- **A webapp plus separate per-session debug runtimes.**
  The webapp serves the catalogue, generation, and verification; each learner session runs in its own `debug-runtime` container, and the database stores the gallery and results. This isolates learner code and lets the product tear down runtimes independently.
- **A browser-based code runner instead of a debug runtime.**
  Would not let the learner use their own VS Code, which the customer chose ([`DEC-004`](../../decisions.md#dec-004)).

## Decision Outcome

Chosen option: one `webapp` (the FastAPI backend and static front end), a `debug-runtime` container per learner session exposing the Debug Adapter Protocol, a `database` for the gallery and results, and a `vscode-extension` client that brings the flow into the learner's own editor per the customer's [`DEC-012`](../../decisions.md#dec-012).
The stack is Python + FastAPI with `debugpy` debug environments, per [`DEC-009`](../../decisions.md#dec-009).
This keeps learner code isolated, lets the product release runtimes on disconnect ([`QR-03`](../../quality-requirements/qr/QR-03.md)), keeps the generator and harness testable from a clean checkout ([`QR-02`](../../quality-requirements/qr/QR-02.md)), and moves the product toward the VS Code extension the customer asked for.

## Consequences

- **Security:** isolating learner code in a `debug-runtime` per session is what lets the product reclaim a runtime and keep no learner code ([`QR-03`](../../quality-requirements/qr/QR-03.md)).
- **Cost:** running a container per session uses the limited VM of [`CON-01`](../../product-vision.md#con-01), so the product must bound how many runtimes run at once.
- **Maintainability:** the split keeps the generator and harness testable from a clean checkout ([`QR-02`](../../quality-requirements/qr/QR-02.md)), because the harness runner is one module and the webapp does not own a process.
